## What Changed Since v0.1.0-rc.3

rc.4 is the first candidate that raises the room-size ceiling, and it closes
every code residual rc.3 shipped as a known limitation. See
`crates/iroh-rooms/CHANGELOG.md` for the full entries.

### Rooms can now hold 40 active members (issues #171 and #173)

`SyncMessage::Events` now fans out over a bounded per-room `iroh-gossip`
overlay among admitted device keys, instead of only over the full mesh of
per-peer links. Each node holds `GOSSIP_BOOTSTRAP_SEEDS` warm links rather than
`N - 1`, which is what makes the ceiling raise safe: full-mesh N=40 crashed the
QUIC layer at 1560 concurrent connections, where the overlay holds roughly six
links per node. `MAX_ACTIVE_MEMBERS` moves 5 -> 40 behind the `large_rooms`
core feature, which is valid only when paired with
`iroh-rooms-net/gossip_overlay`; a compile-time assertion pins the two together
so a mismatched cap/topology build cannot link. Both features are off by default
on their own crates and on in the shipped CLI and the experimental SDK.

Delivery is deliberately dual-path — an `Events` frame still lands on the
destination peer's point-to-point queue when a live writer exists, and the
engine's event-id dedup makes the doubled delivery idempotent. Every pull/query
variant stays point-to-point. Admission is unchanged in kind: `GOSSIP_ALPN` is
gated by the same admission instance as the event plane and closes before the
inner gossip handler runs (threat-model row T26).

**The 40-member ceiling is proven on loopback only.** See Known Limitations.

### Closed rc.3's known limitations

- **Live fan-out to unproven provisional dialers (issue #121).** rc.3 gated
  room *history* behind a capability proof but still pushed chat published
  while an uninvited dialer stayed connected during an open
  `room tail --accept-joins` window. An unproven provisional dialer no longer
  enters the engine's peer set at all: its handshake is deferred until its
  proof verifies or its join upgrades it to a member.
- **Double-connect join-bootstrap gate bypass (issue #126).** A superseded
  link's late close could clear a successor's provisional mark while its writer
  stayed registered, serving an unproven dialer un-gated. Link teardown is now
  a compare-and-swap against a monotonic per-device connection generation.
- **Stale dial loops stomping live links (issue #136).** After a peer rebind,
  an unguarded dial-loop backoff overwrote the peer-table entry of a device
  whose newer inbound link was alive and carrying data.
- **Silently lost store inserts (issue #119).** An accepted event whose store
  insert failed left the fold and store permanently disagreeing. Inserts are now
  retried on a bounded queue, descendants re-place over the healed hole, and
  exhaustion raises a CRITICAL `store_degraded` decision that survives restart.
- **Capability-proof outcomes missing from the audit file (issue #122).** The
  shipped CLI recorded neither accepts nor rejects, when a rejected proof is
  exactly what the local trail exists for. Both now write
  `join.bootstrap.capability_proven` / `capability_rejected` ndjson lines
  carrying the public peer id only.
- **Three silent anti-amplification cliffs.** Exceeding the backfill-depth,
  park-total, or unconfirmed-tip-attempt bounds permanently lost events or
  failed a security gate **open**, while every connectivity signal read healthy.
  Each now raises a CRITICAL trust decision. No bound value changed — raising
  them would move the cliff rather than remove it.

### Local performance guardrails

Byte-bounded priority queues on the event plane (issue #141), a cached
membership projection (issue #142), a bounded early event-id dedup cache with
batched SQLite commits (issue #143), and an observable approach to the
active-member ceiling (issue #144). None changes the wire format, canonical
CBOR, signatures, membership folding, authorization, or the SQLite schema.

## Upgrade Note — rc.3 And rc.4 In One Room

Unlike the rc.2 -> rc.3 upgrade, which broke in both directions, rc.3 and rc.4
peers **do** interoperate — but only while a room stays small.

- **Rooms with five or fewer active members: mixed rc.3/rc.4 works.** The
  dual-path fan-out still delivers `Events` over the point-to-point queue an
  rc.3 peer understands, and no pull/query path, wire format, or event schema
  changed. Such rooms may upgrade peer by peer.
- **Rooms grown past five active members: a coordinated whole-room upgrade to
  rc.4 is required.** An rc.3 peer compiles a hard `MAX_ACTIVE_MEMBERS = 5`, so
  its fold rejects the sixth `member.joined` with `RejectReason::RoomFull`. Its
  membership projection then diverges permanently from the rc.4 peers: events
  authored by members it never admitted fail authorization against its own view.
  Upgrade every member — especially the admin — **before** growing the room.

**Rollback caveat:** a room that has grown past five active members cannot be
rolled back to rc.3. An rc.3 binary will reject the members above the cap and
diverge. Roll back only rooms that stayed at five or fewer.

SDK consumers building from source: issue #141 removes the experimental-tier
`NetConfig::inbound_frame_capacity` / `outbound_frame_capacity` fields in favour
of byte-named budgets. Callers that only override `mode` — the CLI and all SDK
examples — are unaffected.

## Supported Scope

This candidate supports:

- Identity creation.
- Private room creation.
- Key-bound room invites and joins — including joining a room after the
  conversation has started, gated on proof of invite possession.
- Signed room messages.
- Verified file/artifact sharing.
- Authenticated loopback-only live TCP pipes with explicit per-member allow
  lists.
- Explicitly invited agent participants and signed `agent.status` updates.
- Returning-member catch-up across pure-chat gaps up to the 1024-deep backfill
  bound.
- Membership reconciliation independent of room size.
- Up to 40 active members per room, on the gossip-overlay build — see the
  loopback-only evidence caveat in Known Limitations.
- Best-effort local audit trail at `<IROH_ROOMS_HOME>/audit.ndjson`.

## Known Limitations

Read before installing or running this candidate:

- No central application server.
- No guaranteed offline message delivery.
- Local storage is plaintext.
- Invite tickets are password-grade capabilities.
- No native ticket-specific invite revocation; ADR-0002 accepts a bounded
  leaked-ticket model for beta scope only.
- **The 40-active-member ceiling is evidenced on loopback only.** The
  spike-N40 matrix runs in-process endpoints under `NetMode::Loopback` with no
  relay, no NAT traversal, and no discovery. Gate A real-network evidence
  covers two peers, not forty, and was not re-measured for the gossip overlay.
  Rooms materially larger than the previously shipped five members are
  unproven on real networks; treat large rooms as experimental for this
  candidate and see `crates/spike-N40/results/results-gossip.md` for exactly
  what was measured.
- The gossip overlay is a Phase A landing: delivery is dual-path (gossip plus
  the per-peer queue) rather than gossip-only, because the loopback endpoint
  lacks the address-discovery service the gossip dialer needs. At real-network
  scale the gossip path dominates and the queue path coexists as fallback.
- A pure-chat gap deeper than the (finite) 1024-event backfill bound still does
  not fully heal; the chase is bounded by design and membership still converges
  (issue #114 residual, tracked under #102). Crossing the bound now raises a
  CRITICAL `backfill_depth_exceeded` decision instead of failing silently.
- An adversarially wide DAG (thousands of concurrent branches) can hold a
  peer's membership pull in bounded per-tick duplicate re-serves until the
  claim's rotating window anchors; the full answer is the deferred Meyer range
  reconciliation (tracked under #102 and issue #155).
- An oversized event that entered an rc.2 log before the publish-size guard
  existed remains undeliverable to peers (re-served and dropped, now logged).
- `audit.ndjson` is local best-effort audit, not remote, centrally retained,
  tamper-evident, or compliance-grade audit.
- Binary artifacts are checksummed but not project-signed.
- SDK crate remains `publish = false`; SDK use is source/workspace-based for
  this candidate.
- Gate A evidence carries over from the 2026-07-07 refresh; the cellular
  relay-throughput caveat and the missing home-NAT-to-CGNAT reverse-leg waiver
  remain in force.

Closed since rc.3 and no longer limitations: live fan-out to unproven
provisional dialers (#121), capability-proof outcomes absent from the CLI audit
file (#122), store holes from swallowed insert errors (#119), the
double-connect gate bypass (#126), and stale-dial link stomps (#136).

## Security And Privacy Notes

- Storage posture: ADR-0001 scoped plaintext beta on trusted local machines.
- Invite posture: ADR-0002 bounded leaked-ticket model; no native invite
  revocation in this candidate.
- Audit posture: ADR-0003 local `audit.ndjson`; no central retention,
  tamper-evidence, or compliance claim.
- Closed in this candidate: the rc.3 residual where live chat published during
  an open join window reached an unproven provisional dialer (#121); the
  double-connect race that could serve such a dialer un-gated over a successor
  link (#126); and the missing local audit record for capability-proof accepts
  and rejects (#122). The `admin_tip_expired` fail-open — where exhausting the
  unconfirmed-tip attempt budget silently cleared a removal-sensitive access
  suspicion — is now surfaced as a CRITICAL decision rather than passing
  unnoticed.
- New attack surface in this candidate: the gossip overlay adds `GOSSIP_ALPN`.
  It is gated by the same admission instance as the event plane and closes
  before the inner gossip handler runs, so an unadmitted peer receives no event
  bytes (threat-model row T26). The forwarding set remains a subset of admitted
  device keys, so the forwarding-visibility posture is unchanged — but note
  that with the overlay, an admitted member forwards events it did not author
  to other members, which the full-mesh topology did not require.
- Security reporting path: use the private maintainer channel for secrets,
  data loss, authorization bypass, or remote code execution concerns. Public
  bug reports must follow `.github/ISSUE_TEMPLATE/bug_report.md` and must not
  attach full tickets, `identity.secret`, `rooms.db`, blob contents,
  unredacted `audit.ndjson`, or full data-directory backups.

## Compatibility And Migration

- Event schema version: 1 (unchanged from rc.3; the gossip overlay carries the
  same encoded `SyncMessage::Events` body on a second ALPN).
- SQLite `user_version`: 2, unchanged from rc.3. Opening rc.3 data under rc.4
  is a genuine no-op migration — no table is created and the version is not
  advanced.
- Previous Production Beta candidate: v0.1.0-rc.3. The P0.7 previous-candidate
  fixture is committed at `crates/iroh-rooms-core/tests/fixtures/rc3/`,
  generated by the published rc.3 `aarch64-unknown-linux-gnu` binary (checksum
  verified against this repository's rc.3 release notes) and exercised by the
  compatibility gate below.
- **Data continuity is verified in both directions.** An rc.3-created data
  directory opens under rc.4 with `identity show`, `room members`, and
  `room tail --offline` all correct, `PRAGMA integrity_check` OK, and a
  before/after SQL dump that is byte-identical. An rc.3 binary also reads back
  a store that rc.4 has written to, including an rc.4-authored event — so
  rolling the *binary* back does not by itself require restoring a backup.
- Wire compatibility: frame format, ALPN (`EVENT_ALPN`), and event schema are
  unchanged; `GOSSIP_ALPN` is additive. rc.3 and rc.4 peers interoperate in
  rooms of five or fewer active members and diverge past that — see the Upgrade
  Note.

## Rollback

The local store format is unchanged (SQLite `user_version` 2, event schema 1),
and an rc.3 binary was verified to read back a store rc.4 had written to,
including an rc.4-authored event. Rolling the binary back therefore does not by
itself require restoring a backup. Take a pre-upgrade backup anyway — see
`docs/operations/install-uninstall.md` — because the guarantee above covers the
store format, not room membership state.

Rolling back to rc.3 reintroduces live fan-out to unproven provisional dialers
during an open join window (issue #121), the double-connect join-bootstrap gate
bypass (issue #126), stale-dial link stomps after a peer rebind (issue #136),
store holes from swallowed insert errors (issue #119), the missing local audit
record for capability-proof outcomes (issue #122), and the three silent
anti-amplification cliffs. It also drops the active-member ceiling back to five:
**a room grown past five active members cannot be rolled back to rc.3.**
