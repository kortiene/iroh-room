## What Changed Since v0.1.0-rc.5

rc.6's product change is the CLI membership commands, plus one stable-tier
source change that matches the v0.1 plaintext decision. The other reason this
candidate exists is the release workflow already on `main`: it attests
archives and `SHA256SUMS`, keyless-signs `SHA256SUMS`, and self-verifies.
The published run of that workflow is recorded below. See
`crates/iroh-rooms/CHANGELOG.md` for the façade entries.

### CLI `room remove` and `room leave`

The `iroh-rooms` binary gains `room remove <ROOM_ID> <MEMBER_ID>` (admin
only; `insufficient_role`, exit 3, otherwise) and `room leave <ROOM_ID>`.
Both are built on the stable `iroh_rooms::room::build_member_removed` /
`build_member_left` builders (roadmap RB-1.4, `RB-GA-002`, #379).

Removed members lose access to new messages, files, and pipes once peers see
the removal. They keep what they already had. `room remove` seals the removed
device out of admission and forwarding once the removal is folded, including
during the push's flush. `room leave` run again re-syncs the stored
`member.left` (stdout says so; a different `--reason` is not applied) and
does not author a second event. Removing someone already gone is
`not_a_member` (exit 3). These commands do not rotate content keys.

### Stable tier no longer re-exports the rotation builder

`build_member_removed_with_rotation` is no longer re-exported from
`iroh_rooms::room`. It now lives at `iroh_rooms::experimental::rotation`
(with `DistributionError`), behind the `experimental` feature. v0.1 GA ships
room content as plaintext, encrypted in transit only (ADR-0014 OD-1, decided
2026-11-15; roadmap RB-1.2), so the published stable tier does not promise
content-key rotation. Removals on the stable tier use
`iroh_rooms::room::build_member_removed`. This is a source change before the
first crates.io publish. It does not change the wire format.

## Upgrade Note — rc.5 And rc.6 In One Room

**Plaintext rooms, which is every room the shipped CLI operates:** rc.5 and
rc.6 interoperate. Members may upgrade one at a time. This candidate does not
change the wire frame format, the ALPN, the event schema version (1), the
`WireEvent` envelope version (1), the active-member ceiling (5), or the
network topology (full mesh). `room remove` and `room leave` author the
existing `member.removed` and `member.left` events.

**SQLite migration is a no-op.** `user_version` stays at 2. This candidate
adds no table.

**Encrypted writes remain unreachable from the CLI**, as the rc.5 erratum
recorded and ADR-0014 OD-1 decided for v0.1. An embedder that drives the
experimental rotation API still has to upgrade every member past the rc.5
reader-first floor before enabling writers. Nothing in rc.6 changes that
floor.

## Supported Scope

This candidate supports:

- Identity creation.
- Private room creation.
- Key-bound room invites and joins.
- Signed room messages.
- Verified file/artifact sharing.
- Authenticated loopback-only live TCP pipes with explicit per-member allow

- Admin `room remove` and member `room leave` on the CLI, without content-key
  rotation.

## Known Limitations

State these before install or run commands:

- No central application server.
- No guaranteed offline message delivery.
- Five active members per room. The gossip overlay and the paired 40-member
  cap are compiled and tested but not enabled in shipped binaries.
- Local storage is plaintext. The per-epoch room content keys, when an
  embedder uses the engine's rotation API, are stored in the `room_keys`
  table inside `rooms.db` itself. Any copy of `rooms.db` includes those keys
  (ADR-0001; threat-model T28).
- Invite tickets are password-grade capabilities. There is no native
  ticket-specific revocation (ADR-0002).
- **CLI rooms are plaintext.** v0.1 ships room content encrypted in transit
  only (ADR-0014 OD-1). `room remove` and `room leave` do not rotate keys.
  Removed members lose access to new messages, files, and pipes once peers
  see the removal; they keep what they already had. The content-key rotation
  lifecycle remains in the protocol and the sync engine, reachable from
  `iroh_rooms::experimental::rotation`, not from the shipped CLI. For that
  embedder path the rc.5 constraints still apply: a single immutable admin,
  an admin-offline stall (T29), no automatic rotation on `member.left` (T29),
  cleartext metadata (T30), and a reader-first floor (spec
  `content-key-rotation.md` D8).
- `audit.ndjson` is local best-effort audit, not remote, centrally retained,
  tamper-evident, or compliance-grade audit (ADR-0003).
- `v0.1.0-rc.6` archives are signed by approved run 43835416665. Verify with
  `scripts/verify-release-artifacts.sh` and pin that run. An earlier
  unapproved run's attestations remain public and do not match these digests.
  `WAIVER-PBETA-0004` is retired for this candidate. rc.1 through rc.5 remain
  checksum-only.
- SDK package publication status: source-only, `publish = false`
  (`WAIVER-PBETA-0005`).
- Rollback support: the store format is unchanged (`user_version` 2). Rolling
  the binary back does not by itself require restoring a backup. Take a
  pre-upgrade backup anyway.

## Security And Privacy Notes

- Storage posture: ADR-0001 scoped plaintext beta on trusted local machines.
- Invite posture: ADR-0002 bounded leaked-ticket model; no native invite
  revocation in this candidate.
- Audit posture: ADR-0003 local `audit.ndjson`; no central retention,
  tamper-evidence, or compliance claim.
- Content confidentiality posture: CLI-operated rooms are plaintext,
  encrypted in transit only (ADR-0014 OD-1). T27 is not Controlled for the
  shipped CLI. The engine rotation API remains behind the `experimental`
  feature; its residuals are T28, T29, and T30.
- No independent security review (carries `WAIVER-PBETA-0003`, re-acceptance
  pending). ADR-0014 OD-2 accepts that gap for v0.1 GA as well and points at
  the internal self-review plan in `docs/security/v0.1-self-review.md`. That
  plan is not a completed review of this candidate. No new waiver is created.
- Security reporting path: [`SECURITY.md`](../../SECURITY.md). Use GitHub
  private vulnerability reporting for secrets, data loss, authorization
  bypass, or remote code execution. Public bug reports must follow
  `.github/ISSUE_TEMPLATE/bug_report.md` and must not attach full tickets,
  `identity.secret`, `rooms.db`, blob contents, unredacted `audit.ndjson`, or
  full data-directory backups.

## Rollback

Rollback across this release requires a pre-upgrade backup only if you want
one. The local store format is unchanged (SQLite `user_version` 2, event
schema 1, `WireEvent` version 1). Rolling the binary back to rc.5 does not by
itself require restoring a backup. Take a pre-upgrade backup anyway.

There is no room-size constraint on rolling back. The active-member ceiling
is the same in both candidates.

Rolling back to rc.5 removes the CLI `room remove` and `room leave` commands.
It does not change room bytes those commands already authored: those are
ordinary `member.removed` and `member.left` events rc.5 already understands.

Steps:

1. Stop all Iroh Rooms commands.
2. Reinstall the previous binary.
3. Restore the pre-upgrade data backup if you took one and you need it.
4. Run `iroh-rooms identity show`.
