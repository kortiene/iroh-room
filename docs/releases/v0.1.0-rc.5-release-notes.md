## What Changed Since v0.1.0-rc.4

rc.5's headline is the **content-key rotation lifecycle** (issue #191), which
closes the malicious-reader forward-secrecy gap for removed devices. It also
carries the root-cause fixes for the N=40 gossip-overlay load collapse that
rc.4 held out of shipped binaries, and the terminal member-removal delivery
hardening (#194/#195). See `crates/iroh-rooms/CHANGELOG.md` for the full
entries.

### Content-key rotation on member removal (issue #191)

Before this candidate every room event was **signed but not encrypted**:
confidentiality was purely admission-based. The honest-transport revocation
that landed in #196/#197 closes the leak for a removed device running shipped
code, but a **malicious** removed device that patches its own transport could
keep a process subscribed to the public gossip topic (a rendezvous point, not
a secret) and read every content event it could reach, indefinitely.

rc.5 lands the full rotation lifecycle (spec `content-key-rotation.md`):

- **Encrypted content envelopes (steps 3–4).** A `content.encrypted` envelope
  seals the five content-class bodies (`message.text`, `file.shared`,
  `pipe.opened`, `pipe.closed`, `agent.status`) under AES-256-GCM with a
  per-epoch room key, bound to the exact event by a normative AAD. The signed
  envelope, `event_id`, dedup, causal ordering, and the membership fold are
  byte-for-byte unchanged; membership events stay plaintext. Rollout is
  reader-first (D8): a reader release that parses the envelope as
  opaque-but-valid landed before any writer, gated by a per-engine
  compatibility floor (`SyncConfig::encrypted_content_writes`).
- **Key-aware authorization reads (step 5).** The blob-serve and pipe
  open/close projections (`file_shared_hashes`, `pipe_opened`,
  `pipe_is_closed`) decrypt authenticated envelopes and are **fail-closed**:
  an unreadable event contributes nothing (a blob is not served, a pipe is
  not reopened).
- **Rotation lifecycle (step 6).** An admin-authored `member.removed` carries
  an optional inline rotation payload that wraps a new epoch key for every
  remaining Active member; a dedicated `member.key_distribution` event serves
  proactive rotations and post-`member.left` catch-up. The engine adopts keys
  fold-driven, persists them to a new `room_keys` table, and reloads them on
  restart. Same-epoch conflicting commitments poison the epoch and resolve
  deterministically to the smallest `event_id` (D5a), never arrival order. A
  newly-joined invitee requests historical epoch keys via the new
  `WantKeyHistory` / `KeyHistory` sync messages, served as bounded chunks.
- **SUITE_V1 crypto crate (step 2).** X25519 (Ed25519→Montgomery conversion),
  HKDF-SHA-256, and AES-256-GCM wrap/unwrap live in a pure, sans-IO
  `iroh-rooms-crypto` crate with golden-vector-frozen byte layouts.
- **Broad test matrix (step 7).** Multi-epoch rotation, multi-member rooms,
  adversarial file-share/pipe reads, backward-epoch replay rejection,
  cross-partition conflict convergence, paginated/partial key-history
  transfers, voluntary-leave rotation, and poisoned-epoch restart durability.

**Threat-model delta:** T27 moves from "Partial — honest transport only" to
**Controlled** for the malicious-reader case; new rows T28 (epoch key store),
T29 (rotation latency / admin-offline stall), and T30 (metadata-length
leakage) record the residuals. See "Known Limitations" and
`docs/security/threat-model.md`.

**Wire-format note:** `member.removed` gains an optional `rotation` field and
`member.key_distribution` joins the closed content registry as **strict wire
additions**. A pre-rc.5 peer rejects both as unknown content keys, so a room
must upgrade every member past the compatibility floor before enabling
rotation (reader-first, spec D8). Plaintext (non-rotating) rooms are
unaffected.

Two durability/correctness defects in the conflict-resolution path were caught
by the step-7 matrix and fixed before this candidate: the D5a resolution now
**persists** the winning key and its `source_event_id` (a restart no longer
reloads a stale losing key), and the winning key's attribution is made
arrival-order-independent (a same-key re-offer retains the minimum source
`event_id`).

### N=40 gossip-overlay root-cause fixes

rc.4 held the gossip overlay and the paired 5 → 40 member ceiling out of
shipped binaries because the spike-N40 harness measured a delivery cascade.
That collapse is now root-caused to three stacked defects — an iroh-gossip
message-size kill-switch, a fan-out/serve routing split, and a bounded
anti-entropy pull fan-out — plus per-plane inbound accounting, isolated by a
seven-step single-variable experiment ladder
(`crates/spike-N40/results/results-gossip.md`). With all four in place the
corrected loopback matrix is clean at every measured cell.

**The overlay and the 40-member cap remain disabled in shipped binaries.**
Re-enablement still gates on real-network overlay evidence and the admin
fail-closed recovery story. The one change that is active regardless of the
overlay — the bounded rotating pull fan-out — paces a behind node's pulls
across its peers (at the shipped 5-member cap, a sweep completes in ~2 ticks)
without changing the wire format.

### Terminal member-removal delivery (#194/#195)

`member.removed` is now the removed device's receipt-gated final room fact:
the sender deauthorizes immediately but keeps the connection alive briefly
while a bounded terminal envelope drains, and a current peer acknowledges only
after the removal is durably stored. A malicious or stalled legacy recipient
remains best-effort under a five-second grace.

## Upgrade Note — rc.4 And rc.5 In One Room

**Plaintext rooms:** rc.4 and rc.5 interoperate normally and members may
upgrade one at a time. This candidate makes no change to the wire frame
format, the ALPN, the event schema version (1), the active-member ceiling (5),
or the network topology (full mesh) that a plaintext room observes.

**Encrypted/rotating rooms are opt-in and require a coordinated floor.** The
`content.encrypted` envelope and the rotation events are strict wire
additions a pre-rc.5 peer rejects. A room that wants rotation must first
upgrade **every** member to rc.5 (the reader-first floor, spec D8) and only
then enable encrypted writes; a mixed room that enables writers early will
partition. Rooms that never opt in see no behavior change.

**SQLite migration is a no-op.** `user_version` stays at 2; the new
`room_keys` table is created idempotently (`CREATE TABLE IF NOT EXISTS`) as a
re-derivable cache. Opening rc.4 data under rc.5 creates the table if absent
and advances nothing.

Upgrading the room admin first is the sensible order for encrypted rooms,
because the admin wraps and serves epoch keys.

## Supported Scope

This candidate supports:

- Identity creation.
- Private room creation.
- Key-bound room invites and joins — including joining a room after the
  conversation has started, gated on proof of invite possession.
- Signed room messages.
- Verified file/artifact sharing.
- Authenticated loopback-only live TCP pipes with explicit per-member allow
  lists.
- Explicitly invited agent participants and signed `agent.status` updates.
- Returning-member catch-up across pure-chat gaps up to the 1024-deep backfill
  bound.
- Membership reconciliation independent of room size.
- **Optional per-room content encryption with key rotation** (issue #191):
  forward secrecy for post-departure content once every member is past the
  rc.5 compatibility floor and the room opts in.

## Known Limitations

Read before installing or running this candidate:

- No central application server.
- No guaranteed offline message delivery.
- Local storage is plaintext. The per-epoch room content keys are stored in
  the `room_keys` table **inside `rooms.db` itself** — there is no separate
  key store. Any copy, backup, or read of `rooms.db` therefore includes both
  the ciphertext and the keys needed to decrypt all covered history, so the
  database must be handled as a secret (threat-model T28).
- Invite tickets are password-grade capabilities.
- No native ticket-specific invite revocation; ADR-0002 accepts a bounded
  leaked-ticket model for beta scope only.
- **Rooms are still limited to five active members.** The gossip overlay that
  would lift this shipped disabled — see "N=40 gossip-overlay root-cause
  fixes" above. A sixth join is rejected with `room_full`, exactly as in rc.4.
- The gossip overlay itself remains unproven on a real network. The loopback
  matrix is clean after the root-cause fixes, but re-enablement gates on
  real-network overlay evidence. Do not enable `gossip_overlay` for anything
  you care about until that lands.
- **Content-key rotation constraints (issue #191):** rotation is admin-driven
  under a single immutable admin. An admin-offline removal/leave stalls
  forward secrecy until the admin returns (T29). A voluntary `member.left`
  revokes *access* immediately, but the departed member keeps its old epoch
  key and can keep decrypting new content until the admin explicitly authors
  and distributes a rotation that excludes it — **no automatic rotation fires
  on the admin's next event in v1**, so this window is open-ended until an
  operator rotates (T29). Metadata — event existence, type, timing, the
  causal DAG, and an often-effectively-exact body length — stays cleartext
  (T30); length-hiding padding is out of v1 scope. Rotation requires every
  member past the rc.5 compatibility floor (reader-first rollout, spec
  `content-key-rotation.md` D8).
- A pure-chat gap deeper than the (finite) 1024-event backfill bound still does
  not fully heal; the chase is bounded by design and membership still converges
  (issue #114 residual, tracked under #102). Crossing the bound raises a
  CRITICAL `backfill_depth_exceeded` decision instead of failing silently.
- An adversarially wide DAG (thousands of concurrent branches) can hold a
  peer's membership pull in bounded per-tick duplicate re-serves until the
  claim's rotating window anchors; the full answer is the deferred Meyer range
  reconciliation (tracked under #102 and issue #155).
- An oversized event that entered an rc.2 log before the publish-size guard
  existed remains undeliverable to peers (re-served and dropped, now logged).
- `audit.ndjson` is local best-effort audit, not remote, centrally retained,
  tamper-evident, or compliance-grade audit.
- Binary artifacts are checksummed but not project-signed.
- SDK crate remains `publish = false`; SDK use is source/workspace-based for
  this candidate.
- Gate A evidence carries over from the 2026-07-07 refresh; the cellular
  relay-throughput caveat and the missing home-NAT-to-CGNAT reverse-leg waiver
  remain in force.

## Security And Privacy Notes

- Storage posture: ADR-0001 scoped plaintext beta on trusted local machines.
- Invite posture: ADR-0002 bounded leaked-ticket model; no native invite
  revocation in this candidate.
- Audit posture: ADR-0003 local `audit.ndjson`; no central retention,
  tamper-evidence, or compliance claim.
- **Content confidentiality posture: content-key rotation available (opt-in).**
  For rooms that upgrade every member past the rc.5 floor and opt in, T27 is
  **Controlled** for the malicious-reader case — a removed device that keeps a
  patched gossip subscription receives post-removal content only as ciphertext
  it cannot decrypt. Residuals T28 (epoch key store), T29 (rotation latency /
  no automatic post-leave rotation), and T30 (metadata-length leakage) remain
  open and are listed under Known Limitations. Plaintext (non-rotating) rooms
  remain admission-based only, exactly as in rc.4.
- No new attack surface in shipped binaries from the gossip overlay: it is not
  compiled in, so `GOSSIP_ALPN` is not registered. The rotation lifecycle adds
  the `content.encrypted` envelope and rotation events to the closed content
  registry; these are parsed (and rejected as unknown) by pre-floor peers per
  the reader-first rollout.
- Security reporting path: use the private maintainer channel for secrets,
  data loss, authorization bypass, or remote code execution concerns. Public
  bug reports must follow `.github/ISSUE_TEMPLATE/bug_report.md` and must not
  attach full tickets, `identity.secret`, `rooms.db`, blob contents,
  unredacted `audit.ndjson`, or full data-directory backups.

## Rollback

The local store format is unchanged (SQLite `user_version` 2, event schema 1);
the `room_keys` table is an additive, re-derivable cache. Rolling the binary
back does not by itself require restoring a backup. Take a pre-upgrade backup
anyway — see `docs/operations/install-uninstall.md`.

There is no room-size constraint on rolling back, because the active-member
ceiling is the same in both candidates.

**Caveat for encrypted rooms:** an rc.4 binary does not recognize the
`content.encrypted` envelope or the rotation events. Rolling back to rc.4 in a
room that has enabled encrypted writes means the rc.4 peer rejects those events
and can partition from the room. Roll back only rooms that never opted into
rotation, or return every member to rc.5.

Rolling back to rc.4 also reintroduces the two conflict-resolution durability
defects fixed in this candidate (the D5a resolution persistence and
attribution fixes), and forfeits the forward-secrecy protection of the #191
rotation lifecycle.
